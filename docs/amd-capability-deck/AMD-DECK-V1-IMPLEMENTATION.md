# AIONSI AMD Procurement Capability Deck — V1 Implementation

## Objective

Convert the current AMD capability presentation into an evidence-led semiconductor supplier qualification dossier. The deck must tell a clear path from engineering requirement to demonstrated capability, bounded pilot, specialist capacity and ODC scale.

## P0 — External-readiness gates

- Use the approved AionSi logo asset exactly; no recreated or duplicated wordmark.
- Replace PHOTO placeholders with approved leadership photography before any external release.
- Remove sales-like labels such as `BEST FIT` and avoid wording that implies an existing AMD roadmap or approved vendor relationship.
- Separate corporate claims (`30+ tapeouts`, `270+ engineers`) from workbook-specific staffing evidence (`24 named deployed`, `60 proposed DV/PD`).
- Validate every headline metric and every case-study number before external release.
- Keep customer/program names, customer IP, proprietary AionSi IP, architecture-specific confidential detail and internal properties out of the external deck unless explicitly authorized.
- Keep AIV / AI-assisted engineering as controlled governance material until the scope and controls are internally approved.
- Add an explicit evidence/disclosure classification for public, controlled and confidential material.

## P1 — Qualification narrative

- Use the master journey: Requirement → Technical Capability → Evidence → Ownership → Pilot → Delivery → Scale.
- Make the capability story website-aligned: RTL Design, Design Verification, Physical Design, DFT, Analog Layout, AMS Verification, STA & Synthesis, Embedded Services.
- Convert capability slides into engineering work-package entry points.
- Consolidate DV methodology into one strong verification evidence slide.
- Consolidate PD / STA into one physical implementation slide.
- Use the public SoC physical-design case study as a true case study: context, complexity, AionSi responsibility, technical outcome and source/disclosure note.
- Present leadership as technical ownership, not resume summaries.
- Present three engagement models as engineering operating models: Project Engineering, Specialist Pod, ODC.
- Change ODC language to customer-neutral `Customer Work Package / Roadmap` unless AMD roadmap access is formally established.
- Make the qualification path procurement-relevant: Capability Fit → Evidence Review → Technical Workshop → Pilot Work Package → Quality Qualification → Supplier/Security Qualification → Scale.

## P2 — Art direction and technical visuals

- Replace decorative chip graphics with meaningful engineering diagrams.
- Use protocol / verification coverage visuals for DV: AXI, UVM, SystemVerilog, APB, DDR/DDR5, SoC, PCIe, SVA, USB.
- Use a physical implementation flow for PD: Floorplan → Synthesis → Placement → CTS → Routing → STA → PV → Signoff.
- Make the ODC slide show Customer Work Package → AionSi Technical Lead → DV / PD / RTL-System pods → Quality / Metrics / Continuity → Scale.
- Keep brand system consistent: deep navy, AionSi blue/cyan, orange accent, clean technical white space.
- Reduce repetitive rounded-card treatment by alternating evidence charts, engineering architectures, case-study layouts and organizational views.
- Keep a stronger closing slide focused on the next technical qualification step rather than a generic marketing CTA.

## Evidence sources

- AionSi public website and public case studies.
- Supplied `AMD_Data.xlsx` staffing workbook.
- Approved engineering leadership profiles and DV/PD profile evidence.
- Internal AIV governance source material only where explicitly approved.

## External evidence controls

| Evidence class | External treatment |
|---|---|
| Public website / published case study | Green, source-linked |
| Validated profile / leadership evidence | Green/Amber depending on attribution |
| Workbook staffing records | Amber until account owner validates disclosure |
| Named customer/program references | Amber/Restricted until authorization |
| Customer IP / architecture / implementation detail | Restricted / exclude |
| Proprietary AionSi IP that could imply a competing product | Exclude |

## Success criteria

A reviewer should be able to answer, in one pass:

1. What engineering work can AionSi own?
2. What evidence supports the claim?
3. What engineering capacity exists today?
4. What can be started as a bounded work package?
5. How can it scale to a specialist pod or ODC?
6. What information is controlled and how is disclosure managed?
